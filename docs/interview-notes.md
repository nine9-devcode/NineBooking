# โน้ตสำหรับเล่าโปรเจก

เอกสารนี้ไม่ใช่คู่มือทางเทคนิค แต่เป็นชุดคำตอบสำหรับตอนต้องอธิบายโปรเจกให้คนอื่นฟัง
— สัมภาษณ์งาน รีวิวโค้ด หรือส่งต่อให้คนที่มารับช่วง

รายละเอียดที่อ้างถึงอยู่ใน [architecture.md](./architecture.md) · [flows.md](./flows.md) · [data-model.md](./data-model.md)

---

## เล่าใน 60 วินาที

> NineBooking เป็นระบบจองสินค้าออนไลน์พร้อมหลังบ้าน เขียนด้วย Next.js App Router
> ตัวเดียวทำทั้งหน้าเว็บและ API ต่อ PostgreSQL ผ่าน Prisma
>
> ลูกค้าเลือกสินค้า ใส่ตะกร้า ส่งใบจอง แล้วติดตามสถานะได้ ฝั่งเจ้าหน้าที่จัดการสินค้า
> เปลี่ยนสถานะใบจองตามกฎที่กำหนด ออกใบเสนอราคาเป็น PDF ภาษาไทยที่รองรับหลายเวอร์ชัน
> และดูรายงานสรุปยอด
>
> ตัวโปรเจกพัฒนาต่อจากระบบที่ผมเขียนให้บริษัทตอนฝึกงาน แต่รื้อใหม่ให้เปิดเป็น
> โอเพนซอร์สได้ — ตัดบริการภายนอกที่เสียเงินออกทั้งหมด (ที่เก็บไฟล์ อีเมล SMS OTP)
> แล้วแทนด้วยของที่รันในเครื่องได้ทันที `docker compose up` แล้ว `npm run dev` ก็ใช้ได้เลย
>
> ระหว่างรื้อก็ได้ไล่แก้ปัญหาที่ระบบเดิมมีอยู่หลายข้อ ทั้งเรื่องความปลอดภัย
> เรื่อง race condition ตอนออกเลขที่เอกสาร และเรื่องประสิทธิภาพของการค้นหา

## จุดที่ควรหยิบมาเล่า

เลือกเล่า 2–3 ข้อพอ แล้วเล่าให้ลึก ดีกว่าไล่ครบทุกข้อแบบผิวเผิน
แต่ละข้อมีโครงเดียวกัน: **เดิมเป็นยังไง → พังยังไง → แก้ยังไง**

### 1. เลขที่เอกสารชนกันเมื่อมีคนกดพร้อมกัน

**เดิม** ทั้งสามระบบ (ใบจอง / เรื่องแจ้งปัญหา / ใบเสนอราคา) ออกเลขด้วย
`count() + 1` หรือ "หาเลขล่าสุดแล้ว +1" **นอก** ทรานแซกชัน

**พังยังไง** มีช่องว่างระหว่างอ่านกับเขียน สองคนกด checkout พร้อมกันได้เลขเดียวกัน
คนที่เขียนทีหลังชน unique constraint แล้วทั้งคำสั่งพัง — ที่แย่กว่าคือมันพัง
_หลังจาก_ ล้างตะกร้า ลูกค้าเลยไม่รู้ว่าสั่งติดหรือไม่ติด

**แก้ยังไง** ตาราง `DocumentCounter` กับ `upsert ... { increment: 1 }` ซึ่ง atomic
ระดับ row ของ Postgres และ **บังคับให้ฟังก์ชันรับ `tx`** ไม่ใช่ `prisma` ตัวเต็ม
เลขกับเอกสารจึง commit พร้อมกัน ถ้า rollback เลขก็คืนกลับไปด้วย

> เจอบั๊กพ่วงระหว่างแก้: prefix ของเลขสร้างจาก `toISOString()` (UTC) แต่ไปนับจำนวน
> ด้วยช่วงที่สร้างจาก `setHours()` (เวลาท้องถิ่น) พอเป็นเวลาไทย ช่วงเที่ยงคืนถึง
> 07:00 น. สองอย่างนี้คนละวันกัน เลขลำดับเลยรีเซ็ตกลางวัน

ไฟล์: `src/lib/document-number.ts`

### 2. ตรวจชนิดไฟล์อัปโหลดจาก magic bytes

**เดิม** เอานามสกุลจาก `file.name` และเช็คชนิดจาก `file.type`

**พังยังไง** ทั้งสองค่านั้น client ตั้งเองได้ ส่งไฟล์ชื่อ `x.html` ที่ประกาศว่าเป็น
`image/png` แต่ข้างในเป็น `<script>` ได้ ไฟล์ไปวางใน `public/` แล้วถูก serve เป็น
`text/html` บน origin เดียวกับเว็บ → สคริปต์ของคนอื่นรันด้วยสิทธิ์ของคนที่เปิดลิงก์
(`nosniff` ช่วยไม่ได้ เพราะนามสกุลเป็น `.html` จริง ๆ ไม่ได้เกิดจากการเดาชนิด)

**แก้ยังไง** อ่าน magic bytes แล้วให้ตาราง `SIGNATURES` เป็นแหล่งเดียวของนามสกุล
ชื่อจาก client ใช้ได้แค่เป็นส่วนที่อ่านออกของชื่อไฟล์

**ต่อยอด** ไฟล์แนบของลูกค้าย้ายออกจาก `public/` ไปที่ `private-uploads/`
เพราะสกรีนช็อตมักมีเลขออเดอร์ ที่อยู่ เบอร์โทร — เดิมใครเดา URL ถูกก็เปิดของคนอื่นได้
ตอนนี้ต้องผ่าน `/api/files/[...path]` ที่เช็คว่าเป็นเจ้าของเรื่องหรือแอดมิน

ไฟล์: `src/lib/storage/index.ts` · `src/app/api/files/[...path]/route.ts`

### 3. หน้า login บอกได้ว่าอีเมลไหนเป็นแอดมิน

**เดิม** โค้ดเช็ค `role === "admin"` ไว้**เหนือ** `bcrypt.compare`

**พังยังไง** ยิงรหัสมั่ว ๆ แล้วดูข้อความที่ตอบกลับ ถ้าได้ `ADMIN_NOT_ALLOWED`
แทน `INVALID_CREDENTIALS` ก็รู้ทันทีว่าอีเมลนั้นเป็นแอดมิน โดยไม่ต้องรู้รหัสผ่าน
และไม่ถูกนับว่ากรอกผิดด้วย เท่ากับได้รายชื่อเป้าหมายฟรี

**แก้ยังไง** สลับลำดับ — ตรวจรหัสผ่านก่อนเสมอ คนที่จะเห็นข้อความนั้นได้
ต้องรู้รหัสผ่านที่ถูกต้องอยู่แล้ว

**พ่วง** rate limit ต้องมีสองแกน: ต่อบัญชี (5/15 นาที) กันเดารหัสของคนหนึ่ง
และต่อ IP (20/15 นาที) กันการสเปรย์รหัสเดียวข้ามหลายพันบัญชี
และต้องนับ**ก่อน**ตรวจ input ไม่งั้นส่งฟอร์มเปล่าเพื่อเลี่ยงการนับได้

ไฟล์: `src/lib/auth.ts` · `src/lib/rate-limit.ts`

### 4. สถานะใบจองย้อนกลับได้

**เดิม** API เขียนค่าใหม่ทับลงไปตรง ๆ โดยไม่ดูของเดิม

**พังยังไง** เปลี่ยนจาก `CANCELLED` กลับไป `COMPLETED` ได้ ซึ่งไม่มีความหมาย
ในโลกจริงและทำให้ตัวเลขในรายงานอ่านไม่รู้เรื่อง

**แก้ยังไง** เขียน state machine เป็นตารางเปลี่ยนสถานะ (`ORDER_TRANSITIONS`)
`COMPLETED` กับ `CANCELLED` เป็นปลายทาง ไปต่อไม่ได้

ที่ชอบในวิธีนี้คือ **กฎชุดเดียวถูกใช้สองที่** — ฝั่ง API เรียก `assertTransition()`
ฝั่ง UI เรียก `nextStatuses()` มาสร้างปุ่ม ปุ่มที่กดไม่ได้จะมี tooltip
ที่มาจากฟังก์ชันเดียวกับข้อความ error ของ API จึงไม่มีทางที่หน้าจอกับเซิร์ฟเวอร์
จะเชื่อกฎคนละชุด และตรรกะล้วน ๆ แบบนี้เขียน unit test ได้ตรง ๆ

ไฟล์: `src/features/orders/order-status.ts` (+ `order-status.test.ts`)

### 5. ค้นหาแบบ full-text ที่ทนคำสะกดผิดภาษาไทย

**เดิม** `contains` + `mode: "insensitive"` ซึ่ง Prisma แปลเป็น `ILIKE '%…%'`
— sequential scan ทั้งตารางทุกครั้ง ไม่มี index ช่วยได้ ไม่มีการจัดอันดับ
และพิมพ์ผิดตัวเดียวก็หาไม่เจอ

**แก้ยังไง** ใช้สองกลไกของ Postgres คู่กัน: `tsvector` สำหรับคำที่ตรงพร้อมคะแนน
ความเกี่ยวข้อง และ `pg_trgm` สำหรับความคล้าย

จุดที่ต้องอธิบายได้ถ้าถูกถามลึก:

- **เกณฑ์ความคล้ายตั้ง 0.4 ไม่ใช่ค่าปริยาย 0.6** เพราะ "กลอง" กับ "กล้อง"
  ได้แค่ 0.40 — วรรณยุกต์ทำให้ไตรแกรมต่างกัน
- **ตั้งเกณฑ์ด้วย `set_config(..., true)` ในทรานแซกชันเดียวกับ query** เพราะ Prisma
  ใช้ connection pool ตั้งไว้ล่วงหน้าไม่ได้ แต่ละ query อาจได้คนละ connection
- **ทำไมไม่เขียน `word_similarity(...) > 0.4` ตรง ๆ** — ได้ผลเหมือนกันแต่ index
  ใช้ไม่ได้ กลายเป็น seq scan ซึ่งคือสิ่งที่พยายามหนีมาตั้งแต่แรก
- นี่เป็น**ที่เดียว**ในโปรเจกที่ใช้ `$queryRaw` และทุกค่าที่มาจากผู้ใช้ผูกเป็น
  พารามิเตอร์ผ่าน `Prisma.sql` ไม่มีการต่อสตริงเข้า SQL

ไฟล์: `src/features/products/services/search-products.ts`

### 6. client component ลาก Prisma เข้าเบราว์เซอร์

**เกิดจริง** หน้า `/admin/audit-log` เป็น client component แล้ว import ป้ายภาษาไทย
จาก `lib/audit` ซึ่ง import `lib/db` → `lib/env` ทั้งสายถูกลากเข้าบันเดิลเบราว์เซอร์
แล้วพังตอนเปิดหน้า เพราะฝั่งเบราว์เซอร์ไม่มี `DATABASE_URL`

**แก้ยังไง** ใส่ `import "server-only"` บรรทัดแรกของ `lib/db.ts` — ผิดแบบนี้อีก
จะรู้ตั้งแต่ตอน build พร้อมบอกว่าไฟล์ไหนเป็นต้นเหตุ แทนที่จะรู้ตอนผู้ใช้เปิดหน้า

**บทเรียนที่ตามมา** ค่าคงที่ที่ทั้งสองฝั่งต้องใช้ต้องอยู่ไฟล์แยกที่ไม่ import อะไร
จากฝั่งเซิร์ฟเวอร์ — จึงมี `src/lib/audit-actions.ts` แยกจาก `src/lib/audit.ts`
และ `src/lib/roles.ts` ที่ไม่ import อะไรเลย

### 7. ไม่มีร่องรอยว่าใครทำอะไร

**เดิม** ระบบตอบไม่ได้เลยว่าใครยกเลิกใบจอง ใครลบสินค้า ใครตั้งใครเป็นแอดมิน
ฟิลด์เดียวที่บอกตัวผู้กระทำคือ `Quotation.createdBy` ซึ่งเป็น `String` ที่ไม่มี FK ด้วยซ้ำ

**แก้ยังไง** ตาราง `AuditLog` และ `recordAudit(tx, …)` ที่เขียนใน**ทรานแซกชันเดียวกับ
การเปลี่ยนข้อมูล** — ถ้าการแก้ rollback บันทึกก็หายไปด้วย ไม่เหลือร่องรอยเท็จ

สองการตัดสินใจที่มีเหตุผลชัด:

- **เก็บ `entityLabel`** (เช่น `ORD-20260807-001`) ตอนบันทึก ไม่ join ทีหลัง
  เพราะคำถามที่คนถามจริงคือ "ใครแตะใบนี้บ้าง" และของที่ถูกลบไปแล้ว join ไม่เจอ
- **ไม่มีปุ่มล้างบันทึก** ถ้าแอดมินลบร่องรอยตัวเองได้ในคลิกเดียว บันทึกทั้งหมด
  ก็เชื่อถือไม่ได้ ใช้การลบอัตโนมัติเมื่อครบ 365 วันแทน

## คำถามที่น่าจะโดนถาม

**ทำไม Next.js ตัวเดียวไม่แยก backend?**
ทีมขนาดนี้และโดเมนขนาดนี้ การแยกจะได้ความซับซ้อนเพิ่มมากกว่าประโยชน์ —
ต้องดูแล deploy สองชุด จัดการ CORS และเขียน type ซ้ำสองฝั่ง
สิ่งที่กันไม่ให้กลายเป็นก้อนเละคือกฎการวางไฟล์: `app/` มีแต่เส้นทาง ตรรกะอยู่ใน
`features/` หรือ `lib/` ถ้าวันหนึ่งต้องแยกจริง ชั้นที่ยกออกไปก็คือสองโฟลเดอร์นั้น

**ทำไม rate limit เก็บใน DB ไม่ใช่ Redis หรือหน่วยความจำ?**
หน่วยความจำใช้ไม่ได้เพราะ Next รันหลาย worker ตัวนับใน module scope จึงกันอะไร
ไม่ได้จริง ส่วน Redis จะขัดกับเป้าหมายของโปรเจกที่ว่าโคลนมาแล้วต้องรันได้ทันที
โดยไม่ต้องติดตั้งอะไรเพิ่ม ต้นทุนคือเขียน DB หนึ่งครั้งต่อการเรียกที่ถูกจำกัด
ซึ่งคุ้มสำหรับ endpoint ที่ยิงรัวแล้วเจ็บ และ `consume()` ออกแบบให้เปลี่ยนตัวหลังบ้าน
เป็น Redis ได้โดยที่จุดเรียกใช้ไม่ต้องแก้

**SSE กับ WebSocket ทำไมเลือก SSE?**
ข้อมูลไหลทางเดียว (เซิร์ฟเวอร์ → แอดมิน) ซึ่งเป็นสิ่งที่ SSE ทำได้พอดี
มาพร้อม auto-reconnect ในตัว ใช้ HTTP ปกติจึงผ่าน proxy ได้ไม่ต้องตั้งอะไรเพิ่ม
WebSocket จะได้ความสามารถสองทางที่ไม่ได้ใช้แลกกับ infrastructure ที่ต้องดูแลเพิ่ม

**ข้อจำกัดของ SSE ที่ใช้อยู่คืออะไร?**
รายชื่อผู้ฟังอยู่ในหน่วยความจำของ process — รันหลาย instance เมื่อไหร่
แอดมินที่ต่อกับ instance A จะไม่ได้รับข้อความที่ยิงจาก B ต้องมี Redis pub/sub
มาคั่น ตอนนี้ฝั่ง client มี polling สำรองอยู่ ข้อจำกัดนี้เขียนไว้ในโค้ดและใน README แล้ว

**ทำไมกระดิ่งฝั่งลูกค้าเป็น polling แต่ฝั่งแอดมินเป็น SSE?**
แอดมินเปิดหน้าค้างไว้ทั้งวันและต้องรู้ทันทีที่มีใบจองเข้า ลูกค้าเปิดเป็นครั้งคราว
การเปิดสายค้างสำหรับผู้ใช้ทุกคนเพื่อแจ้งเรื่องที่ช้าได้เป็นนาทีนั้นไม่คุ้ม

**ทำไม `OrderItem` ถึง snapshot ชื่อสินค้าซ้ำ ไม่ normalize?**
เอกสารต้องอ่านได้เหมือนวันที่ออก ถ้า join เอาชื่อปัจจุบันมาแสดง พอแก้ชื่อสินค้า
ใบจองปีที่แล้วจะเปลี่ยนตามไปด้วย และเพราะ snapshot ไว้แล้ว FK จึงตั้งเป็น `SetNull` ได้
— ของเดิมเป็น `Restrict` ทำให้ลบสินค้าที่เคยมีคนสั่งไม่ได้ตลอดกาล

**ถ้าจะขึ้น production จริงต้องแก้อะไร?**
สามอย่าง เขียนไว้ในหัวข้อ "เรื่องที่ควรรู้ก่อนเอาไปใช้จริง" ของ README:
(1) storage — เขียน adapter ใหม่ที่มี `saveFile`/`deleteFile` หน้าตาเหมือนกัน
เพราะบน serverless ไฟล์หายเมื่อ deploy ใหม่
(2) mailer — implement interface `Mailer` แล้วเพิ่มเข้า `DRIVERS`
(3) SSE — เปลี่ยนไปใช้ Redis pub/sub ถ้ารันหลาย instance
ทั้งสามจุดออกแบบเป็น interface ไว้แล้ว จุดที่เรียกใช้ไม่ต้องแก้เลย

**ทำไม CI ไม่มีด่านตรวจ schema drift?**
`Product.searchVector` เป็นคอลัมน์ `GENERATED ALWAYS` และมี index `gin_trgm_ops`
ซึ่ง Prisma อธิบายใน schema ไม่ได้ `prisma migrate diff --exit-code` จึงรายงาน drift
ตลอดแม้ไม่มีอะไรผิด เป็นการปิดโดยเจตนาและมีคอมเมนต์อธิบายไว้ใน workflow

**เทสต์ครอบแค่ไหน?**
Vitest ครอบตรรกะล้วนที่ผิดแล้วเจ็บ — state machine ของสถานะ การรวมรายการสินค้าคู่
การตรวจชนิดไฟล์ และตัวอ่าน query ส่วน Playwright เป็น smoke test เส้นทางสำคัญ
ไม่ได้ตั้งเป้าเปอร์เซ็นต์ coverage แต่เลือกครอบจุดที่ถ้าพังแล้วเงียบ

## เรื่องที่ยกไว้ (ตอบตรง ๆ ได้)

การรู้ว่าอะไรยังไม่ทำและ**ทำไมถึงยังไม่ทำ** มีน้ำหนักกว่าการบอกว่าทำครบแล้ว

| เรื่อง                                                                       | ทำไมยังไม่ทำ                                                                                                                          |
| ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| หน้า audit log ยังใช้ offset pagination และ `count()` แบบเป๊ะ                | รอจนข้อมูลโตพอที่จะหน่วงจริง การ optimize ก่อนวัดคือการเดา                                                                            |
| PDF สองไฟล์ยังมี `StyleSheet` ของตัวเอง (รวม 967 บรรทัด)                     | ตัวหนึ่งรับข้อมูลจาก `order` อีกตัวจาก `quotation` ต้องนิยาม input กลาง + mapper สองตัว — และแก้ layout โดยไม่เห็นผลลัพธ์เสี่ยงเกินไป |
| ยังใช้ `middleware` convention เดิม (Next 16.3 เตือนว่าจะถูกแทนด้วย `proxy`) | ยังใช้ได้ปกติและมี codemod ให้ ไม่ใช่งานเร่ง                                                                                          |
| ไม่มี SEO / sitemap / OG                                                     | แคตตาล็อกอยู่หลังการล็อกอิน Googlebot ได้แค่ redirect ไปหน้า login — ทำไปก็ไม่มีผล                                                    |
| `exceljs` ยังมีช่องโหว่ระดับกลางค้างอยู่                                     | วิธีแก้ที่ npm เสนอคือถอยกลับข้าม major ไม่คุ้ม เพราะไม่ได้ส่ง buffer จากผู้ใช้เข้าไป                                                 |
